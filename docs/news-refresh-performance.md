## 运行路径

旧版入口仍保留在 `scripts/newsServer.ts` / `scripts/newsRefresh.ts` / `scripts/generateDailyNews.ts`，对应旧 npm 命令见 `reference/baselines/legacy-package.json`。旧版聚合整轮来源后构建报告，本轮没有维护第二套旧版队列。新版正常入口是 `apps/worker/src/main.ts`；`scripts/collect.ts` 是逐来源执行的手工入口，不能用它代表 worker 并发性能。

普通新版 worker 的链路为：

```text
来源调度 → sources.fetch → 持久 collection_intakes / batches / items
                         → collection.store（每批最多 50 条）
                         → collection.detail（独立详情任务）
                         → content.extract-body / content.analyze
                         → 单篇 publication + events.group
                         → publication.editorial-batch → 全局精选
```

单来源不再等最慢详情读完才保存其他文章。资料提交、试运行准入和后续任务入队同事务；原始批次未处理完时不推进成功 cursor/ETag。来源运行序号防止旧任务覆盖新水位，恢复任务只传批次/条目 ID。

不变资料通过 identity/hash 提前返回，只补缺失的发现记录；无需再次取得全局编辑锁、修订、分析或归组。真实变更仍按全局锁→文章锁重新检查，旧公开投影在同一事务撤销。成功详情复查会更新检查时间，不因时间信号本身制造正文 revision。

有详情配置且 `maxFetches > 0` 的来源，对 listing 信号变化立即复查；本轮 listing 内最近 72 小时发现的已知材料，每 6 小时可在预算内复查。RSS 每 6 小时完整读取一次 listing，以免恒定 ETag 遮蔽详情页修改；普通刷新继续使用 304。移出 listing、超过活跃窗口或无详情配置的材料不做无限期正文轮询，列表详情预算也不是每篇保证。

## 调度与发布边界

| 项目 | 当前行为 |
| --- | --- |
| 并发 | 列表抓取默认 8、存储 2、详情 4、正文 4、分析 2；有界试运行保留原并发和准入约束 |
| 同域隔离 | 列表、详情、正文队列各自使用数据库协调的同域并发上限 2，跨 worker 生效；不是三个队列合计最多 2 个 HTTP 请求 |
| 超时 | 来源尝试 480 秒，详情尝试 90 秒；请求超时与可取消总期限合并。pg-boss 的 600/120 秒过期只作兜底 |
| 详情重试 | 暂时错误最多 3 次业务尝试，30/60 秒退避并尊重 Retry-After；永久错误或耗尽后保留原始材料，沿原公开门槛处理。进程中断的队列恢复另计 |
| 背压 | 未完成原始条目加正文/分析队列达到 2000 时暂停新来源派发，降至 1000 恢复；可用 `COLLECTION_BACKLOG_HIGH/LOW` 调整。单次已返回的大列表仍完整接收，阈值不是硬容量上限 |
| 批次精选 | 首项之后 2 秒唤醒，达到 100 个变更事件立即唤醒；另有 2 秒恢复轮询。排队、全局锁及计算耗时不包含在 2 秒窗口内，不承诺拥塞时 5 秒内页面可见 |
| 安全变更 | 撤回、权限缩减、已有内容修订、改类和管理操作继续同步重评，不等待普通批次 |
| 事件特征 | 相同输入/策略签名且未到时间边界时复用缓存；全局名额、来源多样性和十类语义仍由全候选选择决定 |
| 原始批次保留 | 每日清理完成超过 24 小时且没有未完成尾部的原始批次；文章、抓取统计、回执和未完成批次保留 |

已确认回执继续复用。unknown 超过 30 分钟允许自动放行一次，可能重复计费；再次 unknown 需要人工账单核验。没有新增供应商计费核验服务，也没有开启真实模型或付费来源。

## 对照实验

Apple M5 Max / 128 GiB、Node 24.19.0、PostgreSQL 17.11，本机独立测试库，串行运行时没有 web/worker 或其他本任务基准并发。每组预热 1 次、计量 5 次，使用固定 Git blob 加载优化前实现。完整逐次结果见 [原始数据](benchmarks/news-refresh-2026-10-10.json)。

| 固定工作负载 | 优化前 | 优化后 | 变化 |
| --- | ---: | ---: | ---: |
| 980 未变化 / 10 新增 / 10 修改：整轮耗时中位数 | 319.27 ms | 216.86 ms | -32.08% |
| 同一工作负载：SQL 次数 | 6050 | 3110 | -48.60% |
| 同一工作负载：Node CPU 中位数 | 225.73 ms | 183.94 ms | -18.52% |
| 1000 全新：整轮耗时中位数 | 304.89 ms | 311.16 ms | +2.05% |
| 1000 全新：SQL 次数 | 5000 | 5000 | 不变 |
| 100 篇连续发布：整轮耗时中位数 | 1697.09 ms | 187.39 ms | -88.96% |
| 100 篇连续发布：SQL 次数 | 33249 | 2572 | -92.26% |
| 100 篇连续发布：Node CPU 中位数 | 1227.66 ms | 120.98 ms | -90.15% |
| 100 篇连续发布：全局重算次数 / 最终精选数 | 100 / 40 | 1 / 40 | 选择结果一致 |

混合入库 5 次耗时范围：优化前 316.46–324.62 ms，优化后 214.23–229.62 ms；全新入库分别为 297.42–314.91 ms、307.18–326.35 ms；发布分别为 1657.62–1712.95 ms、185.62–188.08 ms。全新路径没有超过拟定的 10% 回退容忍范围。

这些是两个阶段的微基准，没有网络和模型等待，CPU 只计 Node 客户端、不含 PostgreSQL。5 个整轮样本不能当作逐篇 P95。混合入库本身尚未达到计划的 CPU/SQL 均下降 50% 目标；批次发布明显下降，但不能将两组比例相加或当成生产整体提速。发现到公开 P95 下降 30%、数据库锁等待分布、峰值内存及真实费用仍待独立端到端测量。

## 迁移、恢复与剩余工作

先迁移新 PostgreSQL，再同时更新 API/worker；新表和字段都是增量，不迁移旧 Supabase。新队列在普通 worker 的 `COLLECT_ENABLED=true` 时注册；将它设为 false 会同时停止列表/存储/详情/正文消费者，不能用它作为“停抓取但继续排空”的开关。有界试运行仍通过原显式同步入口运行，不自动开放新的来源调度。

需要回退时，先暂停来源的新任务派发并保留当前消费者，排空 `collection_intakes.finished_at IS NULL` 与 `editorial_batch_state` 未应用 generation，再停止旧消费者、切换兼容版本。无法排空时保留当前版本与数据，不能直接切到不认识新队列的历史版本；不清空队列、不删除迁移、不清除回执。管理/手工 `publishArticle` 默认仍可同步重评。

本轮缓存复用了不变事件特征，但重评仍读取完整事实成员，并在原全局锁内计算和提交；计划中的批量签名读取、锁外快照计算尚未落实。部分来源适配器（如 X shard）保留原路径；正文采样窗口及预算需要按实际来源校准。没有扩充来源、重开历史观察任务或解决 P5 的全部提取/生成质量问题。

S0–S3 的核心提速与离线正确性检查已实现；S4 仍欠完整端到端性能与生产验证。当前仅有旧 Vercel 目标，新平台/预算和账户接入尚未确定，因此没有进行部署切换。
