# 新版部署方案

> 状态：**云部署已暂停**。2026-10-10（Europe/London），用户最新决定先在本地自用和测试；后续工作以[本地新闻与质量计划](local-news-quality-plan.md)为准。无需先购买服务器或选择云平台。本文件保留当天早些时候的云方案快照，恢复云部署时重新核对平台能力、价格与账户接入；不是已购买资源或已经上线的证明。

## 保留方案：Railway 承载完整新版，保留旧站切换入口

新版使用固定 AIHOT 的 web/API/常驻 worker/PostgreSQL 架构。2026-10-10 早些时候核对的 Vercel 生产部署为旧提交 `8912036adff7bd50cfb27a9cf901fcbe31aa788c`；仓库关闭自动部署。本地方案不修改这个公网目标。

Vercel 的 Container Runtime 仍是按 HTTP 流量伸缩的函数，生产无流量 5 分钟会缩容；不能直接把当前 pg-boss 轮询 worker 放进去保持采集。因此推荐完整新版部署到支持常驻进程的 Railway，先拿独立地址验收，再切旧站入口。[Vercel 生命周期](https://vercel.com/docs/functions/runtimes/container#scale-in-behavior)

初始服务布局：

| 服务 | 配置与用途 |
| --- | --- |
| 应用 | 单副本 Docker；web/API/worker 三个进程，共享一个持久数据卷，故障时由进程管理器一起重启；不启用空闲休眠 |
| 数据库 | 独立 PostgreSQL 17 服务及持久卷；通过内网连接；不连接旧 Supabase，不把新版迁移应用到旧库 |
| 对外入口 | 仅 web 暴露 HTTP；API 走同容器 loopback，数据库不提供公网连接；平台提供 HTTPS |
| 本地文件 | 应用卷保存上传文件、反馈附件和缓存。当前代码有跨 API/worker 本地文件访问，不能直接拆成互不共享卷的多个服务 |
| 初始化 | 单次运行 `node scripts/migrate.ts` 和 `node scripts/seed.ts`，后续部署只迁移；部署前先备份新库 |
| 停机 | 至少 210 秒排空窗口，覆盖 worker 195 秒优雅停止；退出后再挂载卷到新实例 |

现有 Dockerfile 可作为构建基础；确定平台后补应用进程管理入口和平台配置。需验证数据卷写权限、终止信号转发、任一子进程退出联动、健康检查和重启后数据保留，不能只用首页 200 验收。[Railway 配置与排空时间](https://docs.railway.com/config-as-code/reference#deployment-teardown)

## 费用与选择

Railway Hobby 最低 **US$5/月**，包含 US$5 资源用量；超出按用量计费。当前容器资源价为内存 US$10/GB/月、CPU US$20/vCPU/月、卷 US$0.15/GB/月、出站流量 US$0.05/GB。[官方定价](https://docs.railway.com/pricing/plans)

用于决策的例子：若应用和数据库合计平均 1 GB 内存、0.1 vCPU、5 GB 卷、10 GB 出站，按上述价格约 US$13.25/月；这是配置用量示例，不是本站实测报价，不含税费和模型调用。建议初期基础设施月预算设为 **US$20–30**，开启费用提醒；硬上限会停服务，不能把它当作持续在线保证。模型/付费采集预算独立保留，不随基础设施额度自动增加。

另一条路线是独立 VPS 运行现有 Docker Compose，通常能减少平台适配，但需自行负责系统更新、备份、HTTPS 和恢复。当前无已有 VPS，本方案不替用户购买。

## 切换步骤

1. 用户选择平台与新增基础设施预算，并在平台自己的登录页面完成账户授权，不在聊天中发送密码或密钥。
2. 创建独立数据库和应用卷，配置私网 `DATABASE_URL`、`SITE_URL`、随机会话/图片签名、管理员密码；凭据仅写平台 secrets。
3. 固定已通过 CI 的合并提交构建；先关闭采集、模型、通知与外部提交，完成迁移、启动和 smoke，读回 `/api/health` 的 release、worker heartbeat 及新库归属。
4. 恢复原来已核验的 Daily News 来源配置和许可，不自动启用 AIHOT 示范源。选择既有可用模型配置与预算后验证真实新闻：抓取→入库→分析→全部动态→精选；旧 P5 质量缺口仍单独记录。
5. 只有新版已有可读内容、错误恢复和数据持久化通过后，才把旧站入口指向新版。旧部署及旧库保留为回退依据；切换时记录具体 URL、提交、迁移版本、来源水位和实测可见时间。
6. 回退先停止新采集并保留/排空持久批次，保持新库和回执，再恢复入口。不可回退到不能消费新队列的进程并丢弃 pending 任务。

恢复云部署时再处理：平台/基础设施预算选择、账户接入、平台配置与实机验证、最终入口切换。信源/模型恢复与质量验证先按本地计划推进，当前不受云平台选择阻塞。提速代码本地测试和 PR 合并不能替代云部署证据。
