# 数据库存储减量计划

日期：2026-10-12；状态同步：2026-10-18（Europe/London）。状态：**PR #24 已合并，本地迁移有历史验收；本机服务已暂停，云库恢复仍待确认**。

## 用户要求与范围

用户明确调整完整报告快照保留为 **3 天**，额外保护当前最新报告及 **1 个可回滚版本**，其余过期快照不再保留，也不另建每日历史归档。其余优化方向认可，要求尽可能减少数据库占用。

本轮覆盖旧 Supabase 的可审查清理迁移，以及当前新版 PostgreSQL 的采集中间数据、队列历史和重复大字段。保持当前新闻阅读、十分类/编辑规则、人工标注、费用对账及任务恢复语义。

完整持久化清单见 [数据库存储清单](../database-storage-inventory.md)。

历史实施分支：`agent/database-storage-reduction`，从本次 fetch 后的 `origin/main=fda2400a7340423e26c8d59e0ab30c41373fd814` 开始。旧 `agent/supabase-retention-cleanup` 中的未提交工作只读参考，不覆盖、不清理。

## 实施策略

| 对象 | 目标策略 | 必须保护的语义 |
| --- | --- | --- |
| 旧完整报告快照 | 保留最近 3 天，额外保护 latest 与沿其 supersedes 链的 1 个回滚版本；其他过期快照分批删除 | 最新指针、真实回滚祖先、不可变约束、刷新锁；回滚过的 latest 不能按全库最新两条替代保护 |
| 旧候选、刷新记录 | 候选 30 天，拒绝候选 7 天；正常已结束刷新 30 天，失败 90 天；小批清理 | 未结束、活跃租约、仍被保留报告引用的数据不删 |
| 新采集中间数据 | 已完整处理的候选立即收缩为最小结果；完整结束 1 小时后清理，小时级执行 | pending/detail retry/未完成尾项保留；游标只在可靠落地后推进 |
| 新成功任务历史 | 高频已完成队列任务保留 1 天；失败保留窗口单独处理，不提前删除待重试任务 | 幂等、singleton、排队恢复、后台失败诊断 |
| 模型/采集回执 | 对可压缩响应做无损 gzip，避免数据库长期保留大 JSON；兼容现有回执，分批收缩存量 | 已收到响应可恢复且不再次付费；逻辑键、请求 ID、token/费用/价格快照保留；损坏响应不自动重发 |
| 文章与版本 | 仅实施经调用路径确认不影响阅读/重评/历史去重的减量；优先移除重复中间副本 | 当前公开内容、人工样本和试运行证据不删除 |

旧快照保护数量为 latest + 1 个回滚版本；三天窗口内其他快照按用户指定窗口保留，窗口外没有额外每日归档或更多回滚副本。

## 阶段与交付

1. S1：旧 Supabase 专用清理迁移、dry-run、分批/锁/权限/引用保护及 SQL 回归。迁移文件由 Supabase CLI 生成；不向旧库执行新版 migrations。
2. S2：新版候选收缩和每小时短期清理、队列完成历史缩短、无损响应压缩及必要兼容迁移。
3. S3：在独立 `_test` 数据库运行相关回归与完整必要检查；用本地数据的受保护副本测量前后有效载荷/关系大小，区分逻辑释放和物理回收。
4. S4：审查 diff，提交、推送 ready PR。代码、CI、真实库应用和空间回收分别记录；平台磁盘恢复与后续云库应用明确保持待执行。

## 验收

- 3 天边界、latest 已回滚到旧版、单份报告、祖先回滚保护、活跃刷新、只读预览、并发/权限、分批执行均有回归。
- 未完成 collection item、详情失败重试、来源游标和回执引用保持；完成数据的重复执行幂等，新闻和人工标签不变。
- 压缩回执往返结果一致；同 logical_key 仍复用；损坏数据不能引发新的模型请求；费用计数不变。
- 队列选项对已有队列生效，而不只是新建队列；pending/retry/active 的恢复能力不变。
- 最小相关测试后运行必要 typecheck/build/web/backend 检查，验收输出记录实际条数，不沿用历史结果。
- 清理空间收益以实测为准，不承诺删除行会立即缩小物理文件。日常任务不执行锁表的 VACUUM FULL。一次性旧云库清理后，为解除实际磁盘超限，需要单独核对并回收物理文件；其结果单独记录。

## 应用和恢复边界

代码默认不启用额外采集、模型或云服务。旧云库应用必须先取得当前连接，核对项目、现有迁移、Cron、活跃租约及数据保护范围，展示 dry-run 后按已授权策略执行。一次性数据清理前保留可恢复备份；不把持续保留更多历史快照作为备份策略。

新版先在数据副本验证。正式运行切换要保证数据库格式与读取代码配套；压缩数据存在后，不得直接回退到不认识压缩格式的旧进程。回退需要恢复备份或先解压还原受影响列。未完成的 PR 不称作已经减小了在线库。

## 运维入口与升级顺序

新版独立 PostgreSQL：

1. 保存备份，保持 `RECEIPT_COMPRESSION_ENABLED=false`，执行本项目 `database/migrations/` 到 0053。
2. 所有 API/worker 更新到支持解码的版本并排空旧进程，再开启 `RECEIPT_COMPRESSION_ENABLED=true`。
3. `node --env-file=.env scripts/compact-storage.ts` 默认只读预览；明确执行时加 `--apply --max-batches 500`。脚本不触发采集、模型或 VACUUM FULL；重复调用可继续处理积压。
4. 后续普通 worker 的小时任务处理到期数据。回退旧读取器之前必须先解压恢复 JSONB，或恢复数据库备份，不能直接回退旧代码。

旧 Supabase 先暂停现有清理任务，再依次应用 `supabase/migrations/20261012223745_storage_retention.sql` 与 `supabase/migrations/20261012224258_bounded_retention_memory.sql`；不能运行新版 migrate.ts。恢复任务前确认最终函数上限为 25，且数据/磁盘验收通过。已应用迁移不得重复执行。

- `select * from public.daily_news_prune_retention();` 默认预览一小批。
- `select * from public.daily_news_prune_retention(false, 25);` 显式处理一批；返回删除与解绑条数，全部为 0 才表示该次积压结束。上限 25，不放大批次或开启长事务循环。
- 函数复用刷新写锁并拒绝活跃租约，保留 latest 与它的直接祖先；仅专用 NOLOGIN 角色能够解除旧引用/删除快照，普通 API 角色不能绕过不可变约束。
- 本轮既有离线备份通过 SHA-256 校验，逐条覆盖全部 2,561 份待删报告；补充当前候选、刷新记录、来源状态和两个受保护报告的本地备份。备份与测试输出保存在忽略目录，未提交新闻正文或凭据。
